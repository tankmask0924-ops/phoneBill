## 一、规则

1、接口地址：在接口账户信息里查看

2、Content-Type：application/x-www-form-urlencoded

3、请求方式：HTTP-POST

4、请求参数：所有参数必须通过URL 编码，编码格式为:UTF8

5、返回参数：格式为json

6、签名验证

　　md5 加密编码格式为gb2312，参数值是未经过url 编码。

### 2、充值回调

| 参数名称 | 参数说明 |
| --- | --- |
| OrderNo | 客户自己订单号 |
| OrderStatus | 充值状态：1 充值成功，-1 充值失败 |
| OrderMessage | 订单状态信息，如：充值成功或充值失败<br><br>话费余额查询在此处显示余额，格式：<span style="color:#FF0000;font-weight:bold">余额：100.56</span><br><br>携号转网查询结果在此处显示，格式：<br><br><span style="color:#FF0000;font-weight:bold">未转网，当前运营商：移动</span><br><span style="color:#FF0000">已转网，当前运营商：电信</span><br><br>空号查询结果在此处显示，格式：<br><br><span style="color:#FF0000;font-weight:bold">号码状态：正常号</span><br><br><span style="color:#FF0000;font-weight:bold">号码状态：空号</span> |
| Voucher | 凭证流水号 |
| Temp1 | 平台订单号 |
| Temp2 | 备用参数，如话费充值前余额 |
| Temp3 | 备用参数，如话费充值后余额 |
| Sign | 签名串，采用md5 加密(编码格式为gb2312)，待加密字符串：<br><br>Md5(OrderNo=\*\*\*&OrderStatus=\*\*\*&key=\*\*\*) |

说明：<br>
　　HTTP-POST 回调通知，Content-Type 为 application/json;charset=utf-8

回调报文示例

```json
{"OrderNo":"100032231113131523100868","OrderStatus":"1","OrderMessage":"充值成功","Voucher":"1101215465644574222","Temp1":"","Temp2":"","Temp3":"","Sign":"c5587dd2c257a02903131af7c19a6740"}
```

成功接收回调后，需返回：SUCCESS，否则系统将多次回调，直到接收到SUCCESS，最多回调3 次

## 我们的对接方式（驱动 `yb`）

- 接口参数：接口地址（接口账户信息里的完整 URL，所有接口同一个地址，按 `Method` 区分）、客户编号（`CustomerID`）、密钥、服务器 IP（下单时作为 `CustomerIp` 传）；回调地址自动生成（`回调域名/notify/supplier/{供应商编码}`），每单随下单传 `ReturnUrl`。
- 只接话费：下单、查单、余额、回调；撤单接口不接，话费余额 / 携号转网 / 空号查询不用。
- 字段对应：`OrderNo` = 提交单号 `attempt_no`，`ProductID` = 供应商商品编码，`Account` = 手机号，`BuyNum` 固定 `1`，`ChargeWay` / `Game` / `Zone` / `Server` 传空串，`CustomerSalePrice` = 这次提交的成本价（供应商商品进价，没有时传 `0`），上游价格比它高时会拒单。上游 `SaleOrderNo`（查单 / 回调里的 `Temp1`）存为供应商订单号。
- 全部接口表单 POST。签名：参数按名 ASCII 升序拼 `k=v&...`（值不做 URL 编码，空值也参与），末尾拼 `&key=密钥`，整串按 GB2312 编码后 md5 小写。
- 返回按 `Status.Code` / `Status.Msg` 和 `Data` 第一条取值；返回不是 UTF-8 时按 GBK 转码后再解析。
- 回调按 `md5(OrderNo=&OrderStatus=&key=)` 验签（不区分大小写），JSON 和表单都能收；通过回 `SUCCESS`，不通过回 `fail`。

| 情况 | 结果 |
|---|---|
| 下单 `Code=success`，`iOrderStatus=1` | 成功（上游不再回调） |
| 下单 `Code=success`，`iOrderStatus=-1` | 失败，换下一个供应商 |
| 下单 `Code=success`，`iOrderStatus` 其他值 | 处理中，等回调 / 查单 |
| 下单 `Code=fail`，`Msg` 是「订单重复提交」 | 处理中：上游已有这笔单，文档要求不能直接判失败，以回调 / 查单为准 |
| 下单 `Code=fail`，其他 `Msg` | 失败，换下一个供应商（文档写明无回调） |
| 下单网络超时、连不上、HTTP 出错、返回无法解析或没有 `Code`（没有拿到返回值） | 立即转异常订单并标为人工处理单：查单结果只记录，回调明确成功 / 失败时交回正常流程（见 docs/project.md 2.5） |
| 查单 `Status=1` / `-1` | 成功 / 失败（`ProcessNote` 作为失败原因） |
| 查单 `Status` 其他值 | 处理中 |
| 查单 `Code=fail`，`Msg` 是「无该订单信息」 | 只记录到这次提交上，订单状态不动；一直没结果的到时转异常人工处理 |
| 查单其他 `Code=fail`、没有 `Status`、返回的 `OrderNo` 既不是提交单号也不是上游单号、没拿到返回 | 处理中，不处理订单 |
| 回调 `OrderStatus=1` / `-1` | 成功 / 失败（`OrderMessage` 作为失败原因） |
| 回调 `OrderStatus` 其他值 | 回 `SUCCESS`，不处理订单 |

## 待和上游确认

1. 请求签名要小写还是大写（回调示例是小写，我们发小写）。
2. 查单返回的 `OrderNo` 是我们的单号还是平台单号（文档表格说是我们的，示例像平台单号；两种我们都认）。
3. 「无该订单信息」文档说 5 分钟后再查仍然没有可判失败，我们目前只记录、不自动判失败，需要的话再放开。
4. `CustomerSalePrice` 按什么比较（是否要求 ≥ 上游售价、保留几位小数）。
5. 回调是否有 IP 白名单要配、`CustomerIp` 是否要和上游登记的 IP 一致。
