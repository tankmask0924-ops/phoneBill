# 卡速售外部接口

上游提供的 `docs/卡速售接口.docx`（Apipost 导出）整理成的文本，接口内容照原文；最后是我们的对接方式、结果判定表和待确认事项。

- 接口地址：`https://{服务域名}/prod-api/module-api/external/...`，全部 `POST`，`Content-Type: application/json`。
- 没有全局 Header / Query 参数，认证靠请求体里的签名。
- 上游只给了：产品列表、产品详情、产品分类、查询用户分类余额、外部下单、回调参数。**没有查单接口。**

## 公共请求结构

所有接口的请求体都是同一个结构，业务参数放在 `data` 里：

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| data | object | 是 | 业务参数 |
| sign | string | 是 | 签名 |
| timestamp | number | 是 | 时间戳（毫秒） |
| appId | string | 是 | 用户 appId |
| appKey | string | 是 | 用户 appKey |

```json
{
  "data": { "...": "..." },
  "sign": "cb109f0bc4c93be8b85985a9cbc9bd1e",
  "timestamp": 1763974149213,
  "appId": "29cd9e0e496e48e9be755f928f500a81",
  "appKey": "e61384f551704865b11edb41d0a97d42"
}
```

## 接口签名认证方法

1. 准备参数：`appId`、`appKey`，毫秒时间戳 `timestamp`（Java：`System.currentTimeMillis()`），请求参数 `data`。
2. 参数排序：`data` 里的参数按键名字典序升序。
3. 参数拼接：遍历排序后的参数，排除空值，按 `keyvalue` 格式拼接（键和值之间、参数之间都没有分隔符）。
4. 签名字符串：`appKey + timestamp + 排序拼接结果`。
5. 对签名字符串做 MD5（`DigestUtils.md5Hex`，32 位小写），得到签名。

示例（下单参数，`timestamp=1763974149213`）签名字符串：

```
e61384f551704865b11edb41d0a97d421763974149213apiapiapiOrderSn20251114buyNum1callbackUrlhttps://605d71f4.r5.cpolar.top/module-api/external/product/getProductInfonumber17636618110productId31
```

签名 `cb109f0bc4c93be8b85985a9cbc9bd1e`。

Java 示例：

```java
public static String createSignNew(Map<String, Object> params, String appKey, String timestamp) {
    StringBuilder sb = new StringBuilder();
    Map<String, Object> sortParams = new TreeMap<String, Object>(params); // 按参数名字典升序
    for (Map.Entry<String, Object> entry : sortParams.entrySet()) {
        if (!StringUtils.isEmpty(entry.getValue()))
            sb.append(entry.getKey()).append(entry.getValue());
    }
    String stringSignTemp = appKey + timestamp + sb.toString();
    return DigestUtils.md5Hex(stringSignTemp);
}
```

> 文档各接口示例的签名都已核对过，确认只有 `data` 里的参数参与签名，`appId` 不参与；值为 null 的参数（如产品列表示例里的 `productName: null`）不参与。

## 回调参数

| 字段 | 类型 | 说明 |
|---|---|---|
| orderSn | String | 订单号 |
| apiOrderSn | String | 商家订单号 |
| orderPrice | BigDecimal | 订单价格 |
| orderStatus | String | 订单状态：1 已支付，3 已完成，4 已取消，5 正在充值 |

接收方响应 `success` 表示成功；不是 `success` 的，3 分钟后再调一次，再失败 5 分钟后再调，以此类推直到成功，最多调 5 次。

文档没写回调的请求方式和格式，**回调不带签名**。

## 我们的对接方式（驱动 `kasushou`）

- 接口参数：接口域名（`https://上游域名`，不含 `/prod-api`；下单、余额、商品列表的路径写在驱动里）、`appId`、`appKey`；选填用户 ID（`userId`，查余额要用，不填余额显示「查询失败：没填用户 ID」）、余额分类 ID（`categoryIds`，不填不传）。
- 只接话费，用下单、余额、产品列表、回调；不用产品详情、产品分类。字段对应：`apiOrderSn` = 提交单号 `attempt_no`，`number` = 手机号，`productId` = 供应商商品编码（上游商品 `id`，可从商品列表里选），`buyNum` 固定 `1`，`api` 固定 `api`。上游下单返回的 `orderNo`（回调的 `orderSn`）存为供应商订单号。`productId`、`number`、`userId` 全是数字时按 JSON 数字发，和文档一致（签名按字符串算，结果相同）。
- 签名按上一节：只算 `data`，去掉 null 和空串（数字 0 参与），按名升序拼 `keyvalue`，前面拼 `appKey + timestamp`，md5 小写。`data` 里的空值参数不发。原始报文（`order_attempts`）里记 `data`、`timestamp`、`appId`，不记 `appKey` 和签名。
- **回调不带签名、上游又没有查单接口**，没法像 Turbo 那样回调后查单确认。做法：每单随下单传的 `callbackUrl` = 自动生成的回调地址 + `?token=`，`token = HMAC-SHA256(提交单号, appKey)` 取前 32 位；回调时按 `apiOrderSn` 重算比对，没带、对不上、`apiOrderSn` 为空的回 `fail`（HTTP 400，上游会重推）。只有拿到我们 appKey 的人才能算出 token，别人伪造不了回调。回调 JSON、表单、查询字符串都能收。
- **没有查单**：定时查单、人工查单都不发请求，按处理中记一条「上游没有查单接口」。结果全靠回调；一直没有回调的订单照常超时（转 `timeout`），由人工到上游后台核实后在后台确认成功 / 失败。下单没拿到明确返回的单转异常人工处理单，同样要到上游后台核实。
- 余额取 `data`（字符串金额）。商品列表每页 100 条逐页取完（`rows` 累计到 `total` 为止，最多 50 页）：`id` 作编码、`productName` 作名称、`price` 作进价、`denomination` 作面值；`carrier` 的取值文档没写全，按商品名里带的运营商名（移动 / 联通 / 电信 / 广电）认运营商；`status=1` 且库存不为 0 才算上架；`categoryName`、`productSn` 作为补充说明。

| 情况 | 结果 |
|---|---|
| 下单 `code=200` 且 `data.success=true` | 受理，处理中，等回调 |
| 下单 `code=200` 但 `data.success=false` | 失败，换下一个供应商 |
| 下单其他 `code`（500 等） | 失败，换下一个供应商 |
| 下单 `code=200` 但没有 `data.success` | 不知道建没建单，立即转异常订单并标为人工处理单（见 docs/project.md 2.5） |
| 下单网络超时、连不上、返回无法解析或没有 `code`（没有拿到返回值） | 立即转异常订单并标为人工处理单 |
| 回调 token 对不上 / 没带 | 回 `fail`，不处理 |
| 回调 `orderStatus=3` 已完成 | 成功 |
| 回调 `orderStatus=4` 已取消 | 失败（换下一家 / 全部失败退款） |
| 回调 `orderStatus=1` 已支付、`5` 正在充值或其他 | 处理中 |
| 定时 / 人工查单 | 不发请求，处理中，只记录 |

## 待和上游确认

1. 有没有查单接口（现在没有，结果全靠回调，一直没回调的要人工处理）。
2. 下单失败时的 `code` 和 `msg` 有哪些；`code=500` 是否一定没建单（现在除 `code=200` 且 `success=true` 外都判失败换下一家，如果 500 也可能已经建单会有重复充值风险）。
3. 回调是什么请求方式和格式（JSON / 表单 / GET），会不会原样保留 `callbackUrl` 里的查询参数（`?token=`，不保留的话所有回调都会被拒、订单全部超时）。
4. 有没有「已退款 / 返销」之类的状态，`4 已取消` 是否一定没扣款、没到账。
5. 产品列表 `carrier` 的取值（现在只见过 `1` = 移动，按商品名认运营商）。
6. 余额接口的 `userId`、`categoryIds` 填什么。
7. 服务器出口 IP 要不要加白名单。
